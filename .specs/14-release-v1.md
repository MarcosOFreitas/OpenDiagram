# 14 — Release v1.0 (open source, single release)

**Status:** agreed plan, written 2026-10-21. Replaces the ordering of [13](13-feature-plan.md) for the release; items of 13 not listed here stay there as ideas for forks.

## Goal

Ship **one** release, v1.0, that a team can install, run, upgrade-free and understand **without the author**. After v1.0 the repository stays open (issues and pull requests accepted) with no promised support; the README says "feature-complete, forks welcome".

Budget: about **15 sessions** (about one month, target 2026-11-20). Estimates below are in sessions and are guesses.

## Decisions (locked 2026-10-21)

| Decision | Choice | Why |
|---|---|---|
| License | **Apache-2.0**, final | OSI open source; permissive fits a project with no maintainer; patent grant. Competitors are AGPL-3.0 (ChartDB, drawDB) or MIT (Azimutt). |
| `@dbml/core` | **Stay on 10.x**; no Web Worker | A parse of a typical diagram (≤ 30 tables) costs ~18 ms vs ~9 ms on 3.x, below perception; `useDeferredValue` covers typing. |
| Real performance cost | **Transfer size**: the `App` chunk is 16.3 MB raw / 2.9 MB gzip and the server sends it uncompressed, with no cache header | Measured 2026-10-21 with `npx vite build` and a search of `server/src/index.js`. |
| Storage | **SQLite is final** (`node:sqlite`, one file). No PostgreSQL, not even as an option | Measured: every call but sign-in takes 2 to 28 ms (p50); load is small and read-mostly. PostgreSQL would rewrite ~170 synchronous queries (4-6 sessions), add a second container, `pg_dump` backups and major-version upgrades for every self-hoster, and only buys several app instances, which v1.0 does not need. An optional second engine doubles the test matrix with nobody to maintain it. |
| Sign-in cost | **Kept** (scrypt, about 40 ms of CPU each, async on the libuv thread pool) | The cost is the protection against password guessing, not a database problem; it only shows when dozens sign in in the same second, and sessions last days. Lowering it would weaken security. |
| After v1.0 | Open, no support; Dependabot security alerts only | The author has no time to continue. |
| Bets, in priority order | MySQL/MariaDB live import > migration script from a diff > PII tags | Only what fits the budget ships (see cut line). |
| Not in v1.0 | SSO (accounts, recovery key and administrator reset are enough for self-hosting), password reset by e-mail code (needs SMTP: new config, secret and outbound connection, and the most likely source of unanswered issues; the recovery key and administrator reset cover it), public hosted instance, notifications, proposed changes, co-editing, SQL Server, in-app LLM, Web Worker parse, general API rate limit (left to the reverse proxy, documented) | Each needs ongoing operation or does not fit the budget. |

**Stretch (only if under budget), in this order:**

Payload: diagram id, title, version and the drift summary; never DBML, `source`, a connection or a credential (same line as invariant 7). **Item 7 decisions (grill-me, 2026-10-22):**

1. **Versions:** MySQL 8.0+ supported and tested (demo: MySQL 8.4 LTS); MariaDB 10.6+ best effort, tried once by hand and documented as such (not in CI).
2. **Database = schema:** the *Database* field is optional for MySQL (it only sets the session default; `validConn` accepts it empty for `type: 'mysql'` only); the schema picker lists the databases the user can see, without `mysql`, `sys`, `information_schema`, `performance_schema`.
3. **Read-only in layers:** `SET SESSION TRANSACTION READ ONLY`, every use inside `START TRANSACTION READ ONLY` ... `ROLLBACK`, `max_execution_time = 30000`, `connectTimeout` 8 s; only `information_schema` and `SHOW`. `test-guardrails.mjs` proves an `INSERT` fails inside the session, as root too.
4. **Privileges:** allowlist (`USAGE`, `SELECT`, `SHOW VIEW`, `SHOW DATABASES`) over `SHOW GRANTS FOR CURRENT_USER() USING` the active roles, on the global scope, the selected databases and their tables; anything else (`EXECUTE` included) is a warning naming privilege and scope; a failed check is `could not verify privileges (...)`; `blockWritable` blocks as for the other engines.
5. **TLS:** the three existing modes; tested against the auto-generated certificate of the demo: `off` connects, `noverify` connects encrypted, `verify` fails on the name. No own certificate for the demo.
6. **Imported:** tables, columns (type as MySQL writes it), defaults, comments, PK, FK with actions, indexes, views with their definition, triggers in the table note, `AUTO_INCREMENT` -> `[increment]`, each `enum(...)` column -> a DBML `Enum schema.table_column`. View lineage: the existing parser after replacing backticks with double quotes; a view it cannot read has no lineage.
7. **UI:** a third *MySQL* choice in the Database drawer (default port 3306) and in the shared-connection form; `uiaudit` screen `drawer-database-mysql`, both themes, 375 px.
8. **Demo and tests:** `demo-mysql` (MySQL 8.4, root / writer / reader) in the default set of `docker-compose.demo.yml`; driver unit tests; `test-guardrails.mjs`; the [12](12-table-selection.md) rules (the shared `filterModel`); `roundtrip.mjs` MySQL -> MySQL identical.
9. **Security:** [05](05-security.md) revised first (read-only layers, privilege allowlist, a rogue server: `disableEval: true`, no `infileStreamFactory` and `flags: ['-LOCAL_FILES']`, `multipleStatements` off); hosts through `assertHostAllowed`; nothing changes for a member, a share-link visitor or an agent.
10. Out of scope: SQL Server, MariaDB in CI, an own TLS certificate for the demo, functions and procedures.

**Item 7b: done 2026-10-22, in one session.** Kept to the table form only (`checks { `expr` [name: '...'] }`): the column form has no name. Only enforced checks are read (Oracle `DISABLED` and MySQL `NOT ENFORCED` are left out). In PostgreSQL each partition stays a table of its own (unchanged; hiding partitions would change the picker and stored selections). Found on the demo servers: MySQL 8.4 escapes the quotes of `CHECK_CLAUSE` (`'`), `@dbml/core`'s Oracle importer cannot read a `date '...'` literal (the demo uses `to_date`), and its PostgreSQL importer reads a schema-qualified domain type back as `shop.shop.type` (a library limit, recorded in [04](04-formats.md)). Proven by `dbml.test.js`, `introspect.test.js`, `mysql.test.js`, `docsModel.test.js`, `test-guardrails.mjs` (PostgreSQL and MySQL) and an import from the Oracle demo by hand (no Oracle import in the e2e); `roundtrip.mjs` unchanged. Plan as decided:  check constraints in the native DBML syntax (column `[check: ...]`, table `checks { ... [name: ...] }`; `@dbml/core` 10 parses them and exports `CHECK` to PostgreSQL, MySQL and Oracle), skipping Oracle's `IS NOT NULL` system checks and PostgreSQL domain checks; partitioning as one line in the table note (`PARTITIONED BY RANGE (created_at)`), method and key columns only.

**Kill criterion for item 7:** if after 2 sessions the read-only session and the privilege warnings are not green on `demo-mysql`, stop, keep the work on a branch, and move MySQL back to [13](13-feature-plan.md) for forks.

**Open design decision for item 8/9:** the diff runs in the browser (History) and in the server (scheduled refresh). The Docker image only copies `server/src`. ## Release checklist (definition of done for v1.0)

- [ ] `(cd server && npm test)` and `(cd web && npm test)` green; `npx vite build` and `node --check server/src/*.js` clean.
- [ ] `bash .github/ci-e2e.sh` green on the release candidate image.
- [ ] `node web/uiaudit.mjs` zero findings on every screen; `docshots.mjs` rerun and every picture looked at.
- [ ] Fresh install from the published image on a clean machine: first account, demo import (PostgreSQL, and MySQL if shipped), share link, backup and restore.
- [ ] Transfer size of the first load and parse times at 30 / 200 tables recorded in *Hosting requirements*.
- [ ] License consistent everywhere (item 1 check); `NOTICE` lists third-party licenses.
- [ ] README, specs and docs pages match the behaviour; README says: feature-complete, no support promised, forks welcome; `SECURITY.md` says reports are read on a best-effort basis.
- [ ] What was not tested is listed in the release notes (for example: Oracle with a real private CA, MySQL with a real cloud TLS endpoint).

## Every item follows the loop of [13](13-feature-plan.md)

Decide (`grill-me` for item 7 and anything touching security) → plan → test first → prove (`verification-before-completion`) → review (`requesting-code-review`, security invariants and UI standard as criteria) → one commit per logical change with spec, README and docs page; the author pushes.

What to improve, by effect on a person (each starts by confirming the number in a visible browser, `performance-optimization` skill):

1. ~~**Pan and zoom**~~ **2026-10-22, second session: mostly a bug, fixed.** In a real window with the GPU (`CDP_GUI=1`, a 170 Hz screen) the idle diagram was already busy: a render loop of ~45 React commits a second, each re-rendering ~16,000 components (the measurements of the derived TableGroup boxes went through `onNodesChange`, and `applyNodeChanges` returned a new array even with nothing to apply), and the whole `Workspace` and every edge re-rendered on each pan frame (`useViewport`). After the fix (frames per second, idle / zoom / pan): 50 tables 43 / 29 / 20 -> 181 / 120 / 36; 100 tables 20 / 13 / 9 -> 178 / 50 / 23; 200 tables 10 / 6 / 5 -> 175 / 13 / 8. What is left at 200 tables is the browser painting a large DOM (a pan profile is 3.1 s of native style/layout/paint against ~1 s of JavaScript): 227 nodes, ~2,200 column rows and ~8,700 `Handle` elements (four per column). Next candidates, only if larger diagrams matter: fewer handles per column, React Flow's `onlyRenderVisibleElements` (no help at the fit-all zoom, where everything is visible).
2. **2026-10-22, second session: in part ours, reduced.** After the render-loop fix the keystroke (in a real window, until the status bar counts the new table) took 139 / 394 / 546 ms at 50 / 100 / 200 tables. Column handles are now drawn only for the columns an edge connects (`handleColumns`): 4,844 -> 1,168 handles at 100 tables, 9,488 -> 2,332 at 200. Keystroke 111 / 254 / ~600 ms; zoom 120 -> 151, 50 -> 83, 13 -> 18 and pan 36 -> 55, 23 -> 28, 8 -> 11 frames per second at 50 / 100 / 200. What is left at 200 tables is the parse (~230 ms, the library's) and painting: an expected limit unless the parse moves off the main thread. Earlier note: **Keystroke until the diagram updates**: the editor stays responsive (deferred parse), but the diagram lags 0.5 s at 100 tables, and the parse is only about a quarter of it: rebuilding nodes, edges and positions on every change is the rest. Profile that path before touching the parser.
3. **2026-10-22, second session: the library's cost, plus a redundant pass of ours, removed.** Left to right is dagre with the TableGroups as compound clusters: at 200 tables 1,435 ms with groups and 94 ms without, spent in graphlib and network-simplex ranking. dagre 3.1.1 is no faster (1.6 s) and moves every table, so it was not taken. Ours: Arrange ran the layout twice (estimated sizes, then measured ones) and re-rendered the canvas twice; a table's size does not depend on its position, so when every visible table is already measured one pass gives the same result. Freeze at 200 tables: Left to right 2.9 -> 1.7 s, the other algorithms ~0.9 -> ~0.5 s; final positions identical for the 5 algorithms at 50 and 200 tables (compared in a real window). What is left is dagre's own time: an expected limit for an explicit, one-off action. Earlier note: **Arrange "Left to right"** (dagre) grows faster than linearly: 1.4 s frozen at 200 tables. The other four algorithms stay under 15 ms.
4. **Open Docs**, 2026-10-22 second session: the stress figures were headless and inflated by the render loop; in a real window after the fixes it took 175 / 243 / 667 ms at 50 / 100 / 200 tables (7.6k / 16.5k / 32.4k DOM nodes), almost all of it the browser's layout and paint of a long page. Each table section now has `content-visibility: auto` (native CSS: off-screen sections are laid out only when they come near; find in page, the index links and printing keep working, checked): 107 / 169 / 473 ms. The rest is an expected limit for one long page. Earlier note: **Open Docs** grows linearly (about 8 ms a table): acceptable.
