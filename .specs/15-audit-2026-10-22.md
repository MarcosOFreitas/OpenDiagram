# 15 — Full audit (2026-10-22) and improvement plan

**Status:** proposal: the plan below waits for the author's choice of what goes in before the release items 8, 9 and 11 of [14](14-release-v1.md).

## Scope and method

One pass over the whole repository after items 7 and 7b, the performance work and the five manual-validation fixes of the day. Checked: the security invariants of `AGENTS.md` against `server/src/index.js`, `auth.js`, `policy.js`, `audit.js`, `presence.js`, `agents.js`; the catalog queries of `introspect.js`; the web bundle, the parse and layout costs; the UI found while validating by hand; tests, CI and release readiness against the checklist of [14](14-release-v1.md).

Evidence gathered: `npm audit` (server and web: 0 vulnerabilities), `npm outdated`, file sizes, the built `server/public/assets`, a timing of `parse` and `layout` with `web/stressdbml.mjs` at 50 / 100 / 200 tables (Node, no browser), and the browser checks of the fixes of the day.

**Not checked in this pass:** a penetration test against a running instance; Oracle query plans on a large real catalog; a real cloud MySQL or PostgreSQL TLS endpoint; screen-reader use beyond the accessible names; the CI e2e job on GitHub (it has only run on a laptop).

Severity: **High** = a security invariant or data loss; **Medium** = a real risk or a visible defect with a cheap fix; **Low** = polish or a corner case; **Info** = a decision to record, no code.

No High finding.

### Database import

| # | Sev. | Finding | Fix |
|---|---|---|---|
| Q1 | Medium (large Oracle catalogs) | The Oracle column query filters with `(owner, table_name) in (select … from all_tables union all select … from all_views)` **without** an owner filter inside: on a database with many schemas the dictionary views are read whole. | Put `where owner in (@IN)` in both halves; the result is the same (check with the Oracle demo and `roundtrip.mjs`). |
| Q2 | Low | PostgreSQL identity columns (`generated … as identity`) are not marked `increment`, while MySQL `AUTO_INCREMENT` is. | Read `attidentity`, write `increment`; unit test of the column mapping, e2e on a demo table with an identity column. |
| Q3 | Low | A PostgreSQL **partial** index loses its `WHERE`: a partial unique index looks like a plain unique one. | Add the predicate as the index `note` (DBML supports it). |
| Q4 | Low | MySQL generated columns lose their expression. | Add `GENERATION_EXPRESSION` to the column note. |
| Q5 | Info, open question | PostgreSQL partitions are imported as tables of their own (`events_2026`); a monthly-partitioned table adds many. Hiding them touches the picker and stored selections ([12](12-table-selection.md)). | Author's decision; if yes: skip `relispartition` tables in import and picker, list them in the parent's `PARTITIONED BY` note, tests from [12](12-table-selection.md). |

### Performance

| # | Sev. | Finding | Fix |
|---|---|---|---|
| P1 | Medium | First load: the `App` chunk is 16.3 MB raw / 1.59 MB brotli. About 15 MB of it are the ANTLR SQL parsers of `@dbml/core` (Oracle 14 MB of source, SQL Server 7.8, Snowflake 4.6, MySQL 4.2, PostgreSQL 4.1), needed only by the SQL **import**. The library has a single entry point and `Parser` reaches the parsers too, so a plain dynamic import may not drop them. | Time-boxed investigation (1 session, kill criterion: no gain without patching the library = record and stop): lazy `importer`, check what Rollup keeps, try an alias of the DBML-only path. Record the first-load transfer size either way (it is in the release checklist). |
| P2 | Low | `layout()` computes a full layout on every parse even when every table already has a place, and throws it away. | Measured: 6 / 9 / 13 ms per parse at 50 / 100 / 200 tables, against 83 / 125 / 238 ms for the parse. One early return; only together with other work in `layout.js`. |
| P3 | Info | The parse itself (238 ms at 200 tables in Node) is the limit of `@dbml/core` 10, accepted in the performance review of the day. | — |

## Plan

Sizes in sessions, like [14](14-release-v1.md). Each item follows the usual loop: failing test first, then the change, then the proof of [07](07-testing.md); a UI item ends with `uiaudit` at zero findings.

| Wave | Items | Size | Done when |
|---|---|---|---|
| **A: quick fixes** | U1 Ctrl+F; S1 sign-in budgets; S3 error answers; U2 plain connection errors; S5 housekeeping; U3 account button name; C2 and S7 docs | 1.5 | unit tests named in the table green; `uiaudit editor-search` zero findings; `http.test.js` covers S1 and S3 |
| **B: import quality** | Q1 Oracle filter; Q2 identity; Q3 partial index; Q4 generated columns; Q5 if the author says yes | 1 (+0.5 for Q5) | `test-guardrails.mjs` and `roundtrip.mjs` unchanged or better; the new cases in the demos |
| **C: resilience** | O1 automatic backups; O2 upgrading notes; T1 Workspace tests | 1 | a backup file appears on schedule in a throw-away container and restores with `cli.js restore`; the Workspace tests fail when autosave or the conflict path is broken on purpose |
| **D: measured bets** | P1 bundle (kill criterion above); S2 DNS pinning; S4 scrypt cost | 1.5 | P1: transfer size recorded, smaller or stopped; S2: stub-resolver test; S4: numbers in [05](05-security.md) and a decision |

Proposed order: A, then B and C, then D, then items 8, 9 and 11 of [14](14-release-v1.md). Waves A to D add about 5 sessions to the 16 of [14](14-release-v1.md); if the month is short, cut from the bottom: D first (keep its P1 measurement, which the release checklist needs), then B's Q2 to Q4.

Out of this plan: P2 and C1 (only together with other work), splitting `introspect.js` per engine, a coverage tool (a new dependency for a number).
